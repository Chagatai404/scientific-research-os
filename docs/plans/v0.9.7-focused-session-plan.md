## Design

### The board lays itself out

- **Zones, not raw coordinates.** A step places things in named zones (title strip, left text column, right figure area, bottom caption strip) or in a slot of a column that stacks by itself; absolute `at` stays available for figures but must sit inside the figure zone. Text wraps to its zone's width and a column pushes the next line down.
- **Measured, not guessed.** After each step renders, the page measures every text and formula box and every drawn shape and reports overlaps and off-board items. In tests that is a failure; in a live lecture the board shifts the new text to the next free slot and tells the lecturer through `board-position`/the next `board-append` result, so the next steps are written correctly.
- **One coordinate space.** Text and drawing go in the same SVG (`foreignObject` or SVG text with measured width) so they scale together at any window shape; formulas keep KaTeX.
- **Checked before play.** `board_script.py check` estimates text extents from the Kalam font metrics and rejects a script whose items overlap or leave the board, with the offending step ids, so a weaker lecturer model gets the same error a strong one does.
- **Verified by looking.** First step of the slice: render `examples/board-lecture-gradient.json` and a STAT303-style lecture at desktop, tablet and phone widths and look at them, to confirm and list the actual symptoms before changing anything. A real-browser test then asserts no overlap and nothing off the board for every example lecture.

### One plan, written before the session starts

The agent writes a **session plan** (plain JSON, validated by the repository, any agent can write it) before the learner sees anything:

- the target, the diagnostic budget (existing five-unit rule) and the stages below;
- **probe tree**: each question carries a local answer key, feedback written per wrong option (distractor-specific), and a rule for the next question (`if wrong → prerequisite question X`, `if correct → skip to Y`). The page runs the tree itself, so the next question appears at once. Free-response questions are reviewed by the agent in the background and never block the next question; their verdict adjusts the lecture plan when it arrives;
- **lecture segments**: complete board scripts for the core path, plus pre-written *repair* segments for the gaps the probe can reveal and *extension* segments for answers that show mastery. The probe result selects segments; the agent is not needed to continue;
- **anticipated questions** per segment ("why", "give an example", "what if") with ready board answers;
- the **handout** (below) and the final check.

Adaptation is therefore two-level: the runtime branches instantly on answers it can judge; the agent revises the plan only at stage boundaries or on a question the plan did not anticipate. Anything the plan does not cover still goes through the existing `wait` / `board-append` loop.

### Stages, each in its own environment

1. **Probe.** One question fills the view. A question strip (Q1…Qn with state) lets the learner see where they are and return to a question; no page scrolling. Answer by typing, choosing, or **holding a key to speak** (transcript shown, one keypress to send).
2. **Handout.** The detailed PDF opens in its own Obsidian tab (never an external browser). The learner reads while the next stage is prepared. Started when ready, not on a timer.
3. **Live lecture.** The board only, full height, with the voice, Pause, Ask (typed or held-to-speak), and a one-line progress bar. No lesson prose, no side panels, no navigation list. Everything written lives in the handout.
4. **Check.** Same environment as the probe, questions chosen from what the lecture covered and from the gaps found.

A stage bar at the top shows Probe → Handout → Lecture → Check. The contents list, questions drawer and related-lessons panel stay on the ordinary reading page for sessions that are not planned lectures; the planned session does not render them. No area scrolls inside another: the page scrolls, or a stage fits the window.

### The handout

- Written in LaTeX from a template modelled on the STAT303 recitations (title block, numbered sections, definition and rule boxes, worked examples, a notation table, exercises with solutions at the end, sources). Detailed means it can be studied from alone.
- Compiled with `latexmk -xelatex` in a scratch folder; the build log is checked, and a document that fails to compile or has undefined references is not handed out.
- Saved in the course or project library in its own directory: *assumed* `<course folder>/Tutor Handouts/<date> <topic>/` (`.tex`, `.pdf`, figures) for a course, `01 Projects/<Project>/Library/<topic>/` for a project, plus a vault note that links the PDF and the session. Existing library conventions win over this default.
- Facts and formulas follow `SOURCE_POLICY.md`; where a course source exists (for STAT303 the extracted lecture and recitation notes) the handout cites it. A handout is teaching material, never learning evidence.
- Timing: the handout is drafted at plan time from the sources and the learner's recorded state, and finished with a short section on the gaps the probe found. The learner reads it while the lecture's audio is prepared.

### Parallel work (researcher's permission, 2026-10-18)

The researcher allows the agent to use subagents and subprocesses where they speed the session up. The natural uses: a subagent writes and compiles the handout (and its figures) while the probe runs; another produces a verified visual or animation for a lecture segment; the voice worker pre-renders the lecture's audio. Rules stay as they are: the lecturer agent owns the plan and what the learner sees, a subagent returns files and a short report, every figure and formula is still verified under `VISUALIZATION_PROTOCOL.md` before it is shown, and a subagent never edits the learner's session state.

### A video instead of drawing it (researcher's direction, 2026-10-18)

When a good YouTube video exists for the exact topic, the lecture plays it instead of the tutor animating the idea. Mechanics are in `references/SESSION_PLAN.md`: a `video` segment names a registry record and the part to play; a different agent vets it (the registry forbids vetting your own find); the board introduces it and a question checks it. Two things stand in the way and are **open**: the Obsidian view forbids embedded players (`frame-src 'none'`), and the registry's "Open" would launch the system browser, which the session must not do. The proposal is a host-owned video pane opened by record id inside Obsidian (the host looks up the address, accepts only a vetted YouTube record). That widens the security model and must be tested in real Obsidian, including whether the player loads; it is slice S8 below.

### Connecting and warming up

- `html_sessions.py start <session>` (or the Obsidian view on open) checks, starts if needed, and **waits for ready** on: the Kokoro live-voice worker, the Whisper worker, the tutor lease. The Start button stays disabled with a visible "Voice warming up… / Voice ready" until each reports ready; a worker that cannot start says why and the session offers captions explicitly rather than silently falling back to a device voice.
- Worker idle time-outs are raised so a session does not lose its voice during a long reading stage; the launcher re-checks at each stage change.
- Starting a process still needs the researcher's one-time approval (stored as a setting), after which it is automatic.

### No unrequested browser

- A written rule in the tutor skill and `LIVE_LECTURE.md`: the session lives in Obsidian; never open Chrome or any browser unless the researcher asks. `vault.py open` uses the operating system's URI handler (`os.startfile`) and prints the URI instead of calling `webbrowser`; a test pins this.

### Speed

Budget each wait, then remove it:

| Wait today | Plan |
|---|---|
| Agent review between probe questions | Local answer key and next-question rules; free responses reviewed in the background. |
| Agent writes the lecture while the learner waits | The whole core lecture is written before the stage opens, and its audio is **synthesised during the probe and handout stages** by the warm worker and cached (the narration registry already keys by sentence). Playback starts with no synthesis wait. |
| First sentence of a live answer (about 1.5 s to 3.4 s) | Phrase-level synthesis (split at clauses, first chunk short); measure Kokoro on the GPU (`onnxruntime-gpu`) against CPU and keep the faster one that fits the shared 6 GB card. |
| A question waits for an agent turn | Play a short pre-rendered acknowledgment the moment the question is sent; answer from the plan's anticipated questions when one matches (shown to the learner as a choice, not guessed silently); otherwise the agent answers with the first board step written immediately (one `board-append` per sentence group, not one batch). |
| Spoken question transcription | Already about 1.1 s warm; keep the worker warm. |

**Honest limit:** with an agent that must run a command to answer, an unanticipated question cannot be instant. The plan makes the common path instant and shortens the rest; it does not make an arbitrary answer instant. The only way to get close to instant on arbitrary questions is a streaming answerer that is not the agent loop (a local model, which competes for the same 6 GB card, or a hosted model, which needs a key, sends text out and changes the "no renderer-initiated AI calls" rule). That is a separate decision for the researcher; this plan does not assume it.
