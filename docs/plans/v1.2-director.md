### B.1 Director and orchestration layer

**One entry point, `engage`.** It is a tool in `ros/tools/director.py` and also the `ros ask "…"` / `ros go "…"` CLI commands.

```
engage(intent: str, kind: "auto"|"course"|"topic"|"research"|"review"|"continue" = "auto",
       target: str|None, title: str|None, deadline: str|None, pace: int|None, materials: str|None)
-> {"playbook", "record", "hub", "opened": [task ids], "jobs": [...],
    "for_agents": [{"task", "kind", "skill", "role"}], "for_you": [...], "portal": url, "vault": {note, uri}}
```

`director.parse_intent(text)` is a deterministic fallback used when `kind` or `target` is missing:
- Verbs: teach/learn/study/review/quiz → learn; investigate/test/is it true/compare/simulate → research.
- A course code (`[A-Za-z]{2,5}\s?\d{3}`) → course.

Agents normally pass structured fields themselves. `engage` appends an `intent` event (data: text, kind, target) and runs a **playbook**. `PLAYBOOKS` is a registry like `ROWS`: `Playbook(name, steps: list[Callable[[Ctx], list[str]]])`. Every step is idempotent through task keys.

| Playbook | Steps (deterministic part, done by `ros`) | Agent tasks it opens |
|---|---|---|
| `course` | Create the course record if missing (`home.init` + `context.link` → `course:<key>` hub in both records); `goal` with deadline/pace; register `Courses/<Course>/Inbox/` | `outline` (syllabus/materials → capabilities + `requires`, lecture/recitation units). Once capabilities exist, triggers open `bundle` tasks for frontier capabilities and `handout` tasks for lecture, recitation and chapter. |
| `topic` | Hub `subject:` or `concept:` in the user-wide record, plus a goal | `scout` (sources for teaching), `outline`, then as `course` |
| `research` | Create the project record if missing; `question:<key>` node recording the user's words verbatim, `framed_by`, `status: framed` | ≥3 neutral `scout` tasks (facets: competing models, null results, validity limits); then `verify` per candidate, `ingest` per paper, a `literature` handout, `gaps`/roadmap for missing capabilities, and an experiment-plan proposal (`authorization: awaiting`) |
| `review` | — | none; it returns the `start --scope review:due` hint |
| `continue` | Run `reconcile` | the next tasks via `work` |

Other director tools:
- **`brief`** (read; it calls `automation.reconcile(mode="call")` first, so it is effectively a write). A cross-record snapshot built from the user-wide record and every linked record:
  - `needs_you`: queue items, each with an evidence summary
  - `happening`: open and claimed tasks by kind/agent/age, running jobs, toolchain warnings
  - `learned`: due count, newly demonstrated or retained capabilities, retention series stub
  - `new`: inbox items, user edits that flowed back, drift
  - `next_action`: one line
  
  The MCP instructions and the skills tell every agent to call it first.
- **`work(by, kinds=None)`** (writes): picks the highest-priority open task across linked records and claims it (first claim wins). It returns `{record, task, brief, skill, role, finish_with, args_hint}` using `tasks.GUIDE`. Priority: `grade`/`answer` > `audit`/`verify` > `run` > `bundle`/`handout` for the next lesson > `outline` > `scout`/`ingest` > others, oldest first.
- **`evidence(subject)`** (read): the evidence packet for any queue subject (B.5).
- **`doctor`** (read): Python and ros version; record problems and index health; vault configured and writable; the PDF ladder from `lib.pdf.detect()`; voice and Manim environments; MCP install state per client; portal port; automation cursor age.

**Human acts stay human.** `approve`, `decide` and `waive` are unchanged (`test_human_acts_are_marked`). The director only presents them, with the packet, in the portal's "Needs your judgement" cards and at the terminal (`ros decide …` still asks for confirmation). `engage` can create `authorization: awaiting` but never approves.

**MCP additions** (`ros/mcp.py`):
- `instructions` text: "Call `brief` at the start of every session. For a new course, topic or question call `engage`. Then loop `work` → do the task with the named skill/role → `finish`, until `work` returns nothing; then tell the researcher what needs their judgement (portal link)."
- `prompts/list` and `prompts/get` with `continue`, `learn {what}` and `investigate {question}`. Claude Code shows these as slash commands, so the director needs no command knowledge.
- `reconcile` on `initialize`.
- The portal and runner start by default (`--portal` defaults to 8737 if free; `--no-portal` turns it off).

There is also an optional `ros install --client claude --hooks`, which merges a SessionStart hook running `python -m ros brief --compact` into `.claude/settings.json`.

### B.2 Automation engine

**Mechanism, evaluated:**

| Option | Verdict |
|---|---|
| A separate `ros daemon` (pidfile or lease) | **Rejected.** It contradicts invariant 3 ("no lease or lock files to clean up"). STAT303_ROLLOUT_FINDINGS shows the failure mode: a warm process kept running stale code and reported ready while broken. It is fragile on Windows and invisible to a prompt-only agent. |
| OS scheduler (cron, Task Scheduler) | Rejected as the mechanism (setup per platform); at most documented as an option. |
| **Reconcile-on-call plus in-process tickers in long-lived interfaces** | **Recommended.** Pure stdlib and cross-platform, with no state that needs cleaning up. Works for a prompt-only agent because `brief`, `engage`, `context` and `work` reconcile. |

**`automation.reconcile(rec, mode: "call"|"tick"|"scan"|"daily", budget_ms=…)`** walks the `TRIGGERS` registry:
- Each entry is `Trigger(name, mode, run(rec, cur) -> dict)`.
- Each trigger is gated on `rec.stamp(...)` or a vault-manifest generation, with cursors cached in `<record>/cache/automation.json`. That file is derived; losing it only re-runs idempotent work.
- A trigger with nothing to do writes nothing.
- An `automation.run` event is appended only when a pass opened tasks, queued jobs or wrote notes. That event is the "what's happening" timeline.

**Where it fires:**
- `mode=call`, budget 5 ms: inside `brief`, `engage`, `work`, `context`, and after every writing tool call in MCP and CLI. That is an extra `api.call("reconcile", rec, mode="call")` in each interface after a `t.writes` call.
- `mode=tick`, every 5 s, and `mode=scan`, every 30 s: from `runner.py` threads in `ros serve` and `ros mcp` (which now serves the portal by default).
- `mode=daily`: the first tick of a new local day.
- With no long-lived process, `ros go` runs ticks and jobs in the foreground until idle; `--watch` keeps it running.

| Trigger | Mode | Effect |
|---|---|---|
| `claims_audit` | call | A new or changed claim with no verdicts → `precheck` (when the project `root` is known) + `request_audits` |
| `approval_runs` | call | An `approval` of an experiment → `run` task for ladder rung 1 (more rungs per B-D Q3) |
| `stale_claims` | tick | An artifact hash changed since its verdicts → audit tasks reopened with a key that includes the hash |
| `goal_material` | tick | Active goals → `roadmap.open_tasks` plus `bundle` tasks for frontier capabilities without a bundle |
| `bundle_gate` | tick | A bundle without a manifest or with changed files → `prepare.check` + `prepare.open_tasks` |
| `renders` | tick | Narration without audio or an animation spec without a render, with an engine configured → `job` tasks (`ros.lib.voice`, `ros.lib.animate`) |
| `handout_gate` | tick | A handout source changed → gate; a new source hash → `job` (`ros.lib.pdf build`) |
| `vault_sync` | tick | New node/edge/event lines since the cursor → incremental `vault.sync` |
| `vault_scan` | scan | Stat walk of managed folders and inboxes → `note.annotate`, `inbox.found` and `ingest` tasks, plus the drift report cache |
| `legacy_ledgers` | scan | A migrated legacy learning ledger was edited → `importers.learning_records` (idempotent) |
| `review_note` | daily | Writes `Reviews/YYYY-MM-DD.md` |

**Jobs: local engines run outside the lock.**
- A job is a task of kind `job`. Its `data.argv` is built only by domain code from the allowlist `{"ros.lib.pdf", "ros.lib.voice", "ros.lib.animate"}`, along with `cwd` (inside the record), `timeout` and `then` (the attach call).
- `jobs` (read) lists only system-opened jobs whose argv validates. `job_done(task, result)` (writes) verifies outputs by hash and attaches them (for example `handouts.attach`).
- `runner.py` claims a job (`by="runner:<host>:<pid>"`), runs the subprocess **without** `registry.LOCK`, then calls `job_done`.
- A crashed runner leaves a claim that lapses after the TTL, so there is still no pidfile.
- One job at a time per process. Every output is content-addressed, so two processes duplicating a job is harmless.

**Concurrency:**
- Appends already take the OS file lock.
- `tasks.claim` becomes first-claim-wins among unexpired claims. `tasks.tasks` becomes a `rec.fold("tasks", …)`, which fixes the O(all task events) cost.
- The vault manifest is SQLite with WAL and short `BEGIN IMMEDIATE` transactions.
- Note writes are atomic (temp file + `os.replace`) and deterministic, so concurrent syncs converge.

**Honesty.** Everything deterministic runs without any agent: record setup, tasks, gates, vault, PDFs, voice/Manim when engines exist, prechecks, review notes, inbox detection, migration. Content work (outline, narration, items, handout prose, scouting, verification, audits, experiment runs, grading) waits as tasks. `brief` and the portal say so plainly, for example "5 tasks wait for an agent (oldest 2 h): open your agent and say 'continue'."

### B.3 Vault design

**Settings.** `home.settings()` / `home.set_settings()` read and write `$ROS_HOME/settings.json` (core, stdlib): `vault`, `vault_root` (default `"Research OS"`), `director_name`, `pdf_engine` (`auto|latex|chromium`), `portal_port` (8737). `vault_set` auto-detects vaults from Obsidian's own `obsidian.json`:
- `%APPDATA%/obsidian`
- `~/Library/Application Support/obsidian`
- `~/.config/obsidian`

**Layout.** Everything Research OS writes lives under `<vault>/<vault_root>/`; nothing outside it is ever written.

```
Research OS/
  Home.md                         MOC: courses, projects, Today, Bases embeds, portal link
  Inbox/                          drop zone (global); every hub also has its own Inbox/
  Courses/<Course>/
    <Course>.md                   course MOC (lectures, recitations, chapters, capabilities, progress)
    Lectures/NN <title>.md        layered L0–L3 note (+ PDF in Attachments)
    Recitations/NN <title>.md
    Textbook/NN <chapter>.md
    Lessons/<date> <title>.md     lesson logs mirrored from the record
    <Course>.canvas               prerequisite map (seeded once, then yours)
  Projects/<Project>/
    <Project>.md                  project MOC
    Questions/ Hypotheses/ Experiments/ Claims/ Sources/ Papers/ Handouts/
    Decisions/<date> <subject>.md
    Decision Log.md
    <Project>.canvas              research graph in lanes
  Knowledge/
    Capabilities/<domain>/<capability>.md   one per capability, across all courses (user-wide record)
    Knowledge.md                  domains → subjects MOC
  Reviews/YYYY-MM-DD.md           daily review: due, learned, decided, new
  Bases/  Knowledge.base  Research.base  Handouts.base  Inbox.base  Reviews.base
  Attachments/<hub-slug>/<slug>.pdf|png|svg
```

**Note types.** `vault.NOTE_TYPES` is a registry:

```python
NoteType(name, folder(node, ctx) -> str, render(node, ctx) -> Note, owned_keys: tuple)
```

Types: `home`, `course`, `project`, `capability`, `lecture`, `recitation`, `chapter`, `handout`, `paper`, `source`, `question`, `hypothesis`, `experiment`, `claim`, `decision`, `decision-log`, `lesson`, `review`, `base`, `canvas`.

**Frontmatter.** Flat scalars and lists only, so it works with Properties, Bases and Dataview:

```yaml
---
ros_id: capability:var-sum        # stable record id; the key of every lookup
ros_record: me
ros_kind: capability
ros_portal: http://127.0.0.1:8737/#node/capability:var-sum?r=me
ros_hash: 3f9a…                    # hash of the generated region + owned keys as written
ros_status: generated              # generated | user-edited | reviewed | draft-unreviewed
title: Variance of a sum
aliases: [var-sum]
tags: [ros/capability, course/stat303, state/demonstrated]
state: demonstrated
next_review: 2026-11-02
up: "[[Research OS/Courses/STAT303/STAT303|STAT303]]"
prerequisites: ["[[Research OS/Knowledge/Capabilities/stat/mean|Mean]]"]
pdf: "[[Research OS/Attachments/stat303/L03 Variance.pdf]]"
legacy: "[[02 Knowledge/box]]"     # link to the pre-1.0 note; it is never edited
---
```

**Link scheme:**
- Path-qualified wikilinks (`[[folder/note|Title]]`), so duplicate titles never resolve ambiguously.
- File names are `<Title>.md`, made safe for Windows and Obsidian (`[]#^|:` removed, reserved names, ≤ 120 chars), with a `-<idhash4>` suffix only on a collision.
- Portal ← vault: `ros_portal` plus an "Open in portal" line.
- Vault ← portal: `obsidian://open?path=<abs path>` and `/vault/<rel>` for PDFs.

**Body:**

```
<!-- ros:begin (generated from the record; edits here pause updates) -->
… generated content (callouts > [!definition], > [!question]- recall prompts, evidence tables) …
<!-- ros:end -->
## My notes
(yours — never touched; flows back to the record as an annotation)
```

**Volatility control.** Notes carry only slow-changing values (state, next review date), never retrievability or other daily numbers. That avoids churn for Obsidian Sync, iCloud and OneDrive.

**Two-way sync protocol:**

| Observed in the vault | Rule | Record effect |
|---|---|---|
| Generated region and owned keys equal `ros_hash` | Update freely when the record changes | — |
| Text outside the markers changed (for example "My notes") | Never touched | `note.annotate` event (subject `ros_id`, data `{path, sha, text ≤ 20 KB, prev_sha}`): shown in the portal, readable by agents, **never learning evidence** |
| Generated region or an owned key edited by the user | Note kept, status `user-edited`, updates paused (pinned) | `note.annotate` with the diff summary; Director "Your edit to X diverged — let the record update it?" → `vault_resolve(action="update")` appends `note.release`. The user's text is kept in the event and re-appended under "My notes". |
| `ros_status: reviewed` set on a draft (AI-written) note | Accepted | `note.reviewed` (actor `vault`). This meets SAFETY's "researcher's review before curated", and it is not one of the three human acts. |
| Generated note deleted | Not recreated | `note.dismiss`; `vault_resolve(action="restore")` brings it back. Structural notes (MOCs, Home, Bases) are always regenerated. |
| Note moved or renamed by the user | Manifest re-keys it by `ros_id` | — |
| New file in an Inbox, or a note under `Research OS/` without `ros_id` | Never moved or edited | `inbox.found` (path, sha, hub inferred from folder). Markdown becomes a `source` node (kind `note`) at once; a PDF or image becomes an `ingest` task (librarian: paper / syllabus / slides / textbook / problem set / handwritten → notes-to-latex). |
| Broken wikilinks, missing exports, orphaned attachments | Reported by `vault_status` | Derived and not stored. **Nothing is ever deleted automatically.** |
| v1.1 `ros_export:` notes | Converted in place if unedited; edited ones are left and linked | — |

**The only deletion rule:** `ros` deletes only files it generated whose current hash equals what it wrote.

**Manifest / index.** `$ROS_HOME/vault/index.sqlite`. It lives outside the vault, is derived, and can be rebuilt from the `ros_id` frontmatter. Tables:
- `files(path PK, mtime_ns, size, sha, ros_id, record, kind, gen_hash, owned_hash, user_hash, status, title)`
- `ids(ros_id PK, path)`
- `titles(title, path)`
- `links(src, dst)`

Costs: lookups by id, title or kind are indexed. `scan` stats only `Research OS/` and the inboxes and hashes only files whose (mtime, size) changed. A full-vault walk happens only in `migrate`, `migrate_check` and `vault_status --deep`.

**Incremental sync.** A new core helper, `Record.since(cursor) -> (cursor', node_ids, edge_ends, event_rows)`, reads only new log tails (nodes and edges from byte offsets; events via `seq`). The affected notes are: those nodes, edge endpoints, item→concept for attempts and grades, and their hubs and MOCs. A full render happens only on the first sync or an index epoch change.

**Tools** (`ros/tools/vault.py`):

| Tool | Writes? | What it does |
|---|---|---|
| `vault_set(path?, root?, dry_run=true)` | yes | Detects/sets the vault and reports what the first sync would create |
| `vault_sync(scope?, dry_run?)` | yes | Renders changed notes |
| `vault_status(deep?)` | no | Edited, dismissed, missing, stale, broken links, orphans, inbox |
| `vault_find(q?, kind?, id?, tag?, limit?)` | no | Indexed search |
| `vault_note(id)` | no | Path, URI, PDF, portal URL |

`export --kind obsidian` delegates to `vault.sync` with an explicit path. `ExportTests` is updated for the new layout.

### B.4 PDF handout engine

**Kinds:** `handouts.KINDS`, each a `Kind(name, sections, compose(rec, scope) -> skeleton, rows)`.

| Kind | Scope | Composed from the record (deterministic) | Written by the agent (`handout` task) |
|---|---|---|---|
| `lecture` | a lecture unit (capabilities in `Learning.order`) | Titles, prerequisites, bundle narration (with its locators), looked-at visuals, notation | L0 gist, L1 ≥3 recall prompts (collapsed answers), L2 lecture, L3 derivation and sources (the legacy 25_Lecture_Note format) |
| `recitation` | a problem-set unit | Prerequisite links, worked-example seeds from narration | ≥5 exercises with **full** solutions in an appendix, common mistakes. Exercises are handout-local and **never** assessment items. |
| `chapter` | a hub, subject or course part | Capability tree, definitions already sourced | Textbook chapter: definitions, propositions/proofs, worked examples, exercises with solutions, notation table (the STAT303-recitation quality bar) |
| `literature` | a question | Scout coverage (searches run), verified EvidenceAtoms rendered through `lib.validate_evidence.render` (verdict + locator), `paper`/`source` nodes, competing models / null results | Synthesis prose, gaps, what to read next |
| `findings` | an experiment or claim | Plan, approval event, ladder, run manifests with hashes, result tables from CSVs, claims with per-step verdicts and auditor notes, the adversary memo, defence questions | Interpretation, limitations, decision memo (labelled as a proposal) |

**Record layout:**
- `handouts/<id>/source.json` (skeleton and sections, each section `{id, role, text, locators, by}`)
- `handouts/<id>/figures/`
- `handouts/<id>/manifest.json` (gate verdict)
- `handouts/<id>/build/<source_hash>.{tex,html,pdf,log}`

The `handout:<key>` node has `about` edges (capabilities, claims, question) and `cites` edges (sources, papers, claims).

**Pipeline.**
1. `handout_create(kind, scope, title)` composes the skeleton and opens `handout` tasks for the sections without prose.
2. The agent calls `handout_write(handout, section, text, by)`. Text is Markdown with LaTeX math and fenced blocks (`:::definition`, `:::example`, `:::exercise` … `:::solution`). Each write appends a `handout.revise` event for provenance.
3. `handout_check` runs `handouts.ROWS` (the same `Row` pattern as prepare; a failing row opens a task):
   - `sources` (locator or `derivation: true` per factual section)
   - `no keys` (no item `answer`/`explanation`/`rubric`/`option_feedback` text present: invariant 6)
   - `math` (reuses `prepare._math_problems` + KaTeX)
   - `structure` (kind-specific minimums)
   - `figures` (exist + looked-at)
   - `pdf` (task kind `job`, never blocking)
   - `review` (a warning only: "unreviewed by you")
4. `handout_build(handout, wait=false)` renders three ways:
   1. The **Obsidian note** (native Markdown with callouts and collapsible solutions), always written. This is the primary artifact, so study is never blocked by a compiler (a lesson from v0.9.8).
   2. A **LaTeX source**, from a stdlib Markdown-subset→LaTeX converter onto the restored `roshandout.sty`/`template.tex`, with the environments definition, rulebox, keyidea, commonmistake, workedexample, `\exercise` + `\printsolutions`, and sources.
   3. A **self-contained HTML** using vendored KaTeX and print CSS.
   
   Then it queues a `job`: `python -m ros.lib.pdf build --dir handouts/<id>/build --source <hash> --engine auto`.

**`ros.lib.pdf` ladder**, detected by `detect()`; each step is tried only if the previous is absent or fails:
1. `latexmk -xelatex` / `xelatex` (MiKTeX/TeX Live; `ROS_MIKTEX_BIN`). This restores the legacy `compile_document` and `analyze_log`, with shell-escape off, the installer off, the `FORBIDDEN` command lint, scratch directories outside the vault, a timeout and process-tree kill.
2. `tectonic` (if installed; it may fetch packages, so it is used only when it is the user's chosen engine).
3. Headless Chromium-family browser: Edge on Windows, Chrome, Chromium, or Playwright's at `ROS_BROWSER`. Command: `--headless --print-to-pdf --no-pdf-header-footer --virtual-time-budget=10000`, with KaTeX rendered by the vendored JS.
4. None: the `pdf` row fails with "PDF needs a toolchain: MiKTeX/TeX Live or Edge/Chrome". The job stays waiting, `doctor` and the Director show it once, and the Markdown note is still delivered. **Never an exception.**

Pandoc is used only as an optional higher-fidelity Markdown→LaTeX converter when present. Reportlab is not used: it is not stdlib-adjacent and cannot render math.

**Caching.** `source_hash = sha256(canonical(source.json) + template version + engine)`. An existing `build/<hash>.pdf` is reused with no recompile. `handout.built` (data: hash, engine, pages, bytes) is appended once per hash.

**Placement and links:**
- The PDF is copied to `Attachments/<hub>/<Title>.pdf` only when the hash changed.
- If the vault copy's sha differs from what was last written (for example a PDF annotation plugin edited it), the new version is saved as `… v2.pdf` (legacy rule) and the old one is kept.
- The handout note embeds `![[…pdf]]`, and its frontmatter carries `pdf`, `ros_id: handout:<key>` and `ros_portal`.
- The portal links `/vault/<rel>` and `obsidian://`.

### B.5 Portal redesign

**Server** (`serve.py`, interface):
- A `RecordPool` (shared with `mcp.py`); every `/api/<tool>` accepts `?record=`.
- `GET /vault/<rel>`: read-only, confined to `<vault>/<vault_root>` plus attachments referenced by the record. Allowlisted types (pdf, png, jpg, svg, md); no dotfiles; symlinks resolved inside the root.
- `runner.start(pool)` on startup.
- Port 8737 by default. If it is busy with another `ros serve` (detected via `GET /api/status` and a `Server: ResearchOS` check), print that URL and open it instead of failing.

**Navigation** (≤ 6 rail links): **Director** (home), **Learn**, **Research**, **Graphs**, **Vault** (replaces Library and absorbs lesson logs), **History**. A record switcher and search box sit at the top of the rail.

**Director home** (`views.director`, from `brief`):
1. **Needs your judgement.** One card per queue item with the packet from `evidence(subject)`:
   - per-step verdict chips (expand for auditor notes and checklist)
   - the numbers precheck
   - citations with verifier verdicts and locators
   - experiment plan, approval and run manifests
   - adversary memo
   - defence ownership
   - links: findings PDF, vault note, chain graph
   
   The existing forms stay: `by` is prefilled from `director_name`, and decide needs a rationale. That is one textarea and one click.
2. **What's happening:** tasks by kind/agent/age, jobs, toolchain notices, last automation runs.
3. **What you learned / next:** due reviews (Review now), the next lesson, retention sparkline, newly demonstrated capabilities, unreviewed handouts (Mark reviewed).
4. **New in your vault:** inbox, edits that flowed back, drift actions.

**Graphs** (`views.graphs`): one generic SVG renderer for server-positioned nodes, `drawGraph({nodes:[{id,x,y,w,label,cls}], edges})`, with viewBox pan/zoom. It replaces `drawMap`. Modes:
- Knowledge overview: hubs as clusters with state counts; click to focus a 2-hop neighbourhood (≤ 300 nodes).
- Research lanes: question → hypothesis → experiment → claim → evidence/source/paper, coloured by status, verdict and ownership; the needed capabilities show the user's state.
- Evidence chain: vertical layout for one claim.
- Progress: bars and sparklines.

Clicking a node shows detail with vault/PDF/portal links and Start lesson / Open chain.

**Vault** (`views.vault`): search via `vault_find`, lists by kind, open in Obsidian / open the PDF / open the node, and the drift panel with `vault_resolve` actions.

**Budget estimate:** +6 KB Director, +7 KB Graphs, +4 KB Vault, +3 KB evidence card, +2 KB switcher/search, minus about 2 KB for the removed `drawMap`. That is about 44 KB of 60 KB JS and about 12 KB of 20 KB CSS. Layout is computed in Python (`atlas.layout`, a layered barycenter in O(V+E)), which keeps the JS small.

**Atlas tools** (`ros/tools/atlas.py`):
- `atlas(mode: knowledge|research, focus?, depth=2, limit=300, as_of?)`
- `chain(claim)`
- `progress(since?, as_of?)`: weekly buckets from a `rec.fold("progress", ("grade","retrieval","attempt"), …)` — graded-unaided correct, reviews done, newly demonstrated (first-date fold), due backlog
- `find(q, limit)`: node titles across linked records plus `vault_find`

### B.6 CLI redesign (`ros/cli.py`)

**Zero-config:**
- Bare `ros` runs `brief` and prints a compact text summary with one `→ next:` line.
- If there is no record at all, it offers to create `me --user-wide`, detects vaults and asks once, then runs `vault_set`.
- `home.resolve` falls back to the record with role `user` when there is no selector and several records exist. It also maps cwd to a record whose `record.json` has `repo`, and suggests close names (`difflib`) on a typo.

**New commands:**
- `ros ask "teach me STAT303"` and `ros go "…"`: `engage`, then a foreground runner until idle, with progress lines (`[2/5] pdf L03 Variance (latex)… ok 4 pages`).
- `ros go` with no text: continue.
- `ros doctor`.

**Aliases** (`ALIASES` dict): `b`→brief, `st`→status, `r`→`learn review:due`, `open`→`serve --open`, `q`→queue, `v`→vault_status.

**Errors:**
- An unknown command gives "did you mean …".
- `KeyError` messages name the nearest ids.
- Exit codes are unchanged.

**Speed (F07).** Import the tool modules lazily for the bare and `ask` paths where possible, and keep building only the subparser named.

### B.7 Migration completion and verification

- **New `IMPORTERS` entries** (A.2 table): `projects`, `notes`, `papers`, `legacy_tasks`, `visuals`, `resources`, `handouts`, `session_notes`. All use deterministic `event_id`s and `_sync_nodes`/`_sync_edges`.
- **`migrate`** runs all of them in a fixed order, then:
  - `coverage(vault)`: a classifier per file with categories `learning`, `session-state`, `session-note`, `session-derived`, `research`, `evidence`, `paper`, `index-derived`, `research-tasks`, `visual`, `resource`, `handout`, `project-note`, `note`, `template`, `plugin/runtime`, `attachment`, `unknown`.
  - For each file: `imported` (proved by looking up the node/event whose `source`/`path` names it) or `derived`/`retired` (with a reason).
  - The `migration-report.json` gains `coverage` and `ok = answers_ok and unknown == 0 and not_imported == 0`.
- **`migrate_check`** (read) produces the same report without writing.
- **Idempotence:** a second `migrate` reports 0 nodes, edges and events written.
- **Fixture:** add a `Tutor Handouts/2026-10-01 Box/handout.json` + `.pdf` + note, a `RES-*.resource.json`, a stateless tutor-session `.md`, and an unreferenced evidence atom, and update `manifest.json`. The test asserts every file in `manifest.json` is classified and accounted for.

## D. Risks, decisions, open questions

**Architecture-invariant risks**

| Risk | Mitigation |
|---|---|
| The domain grows a "god orchestrator" | Behaviour lives in registries (`TRIGGERS`, `PLAYBOOKS`, `NOTE_TYPES`, `handouts.ROWS`); `director` only composes. ARCHITECTURE recipes say where each addition goes. |
| Long work under `registry.LOCK` | Jobs run in runner threads outside the lock. A `mode=call` reconcile has a 5 ms budget and defers heavy triggers to ticks. Later, move `bundle_voice`/`bundle_animate` to jobs too. |
| Storing derived values | Drift, broken links, progress and layouts are computed, never stored. Only facts become events (the user wrote X, a file appeared, a PDF was built with hash H). Automation cursors and the vault manifest are rebuildable caches outside the truth. |
| Human acts leaking | No tool besides `approve`/`decide`/`waive` changes authorization or outcomes. A vault edit can never approve or decide; it becomes an annotation at most. The test pinning the human set is unchanged. |
| AI prose presented as curated (SAFETY) | Agent-written notes and handouts carry `ros_status: draft-unreviewed` and a header line naming the author agent until `note.reviewed`. |
| Item keys leaking through handouts | The `no keys` row, plus exercises that are handout-local, never items. |
| MCP tool list growth (61 → ~85) | Keep help lines short. `work` and `brief` mean agents need only a few tools per turn. |

**Performance:** benchmark additions to the `ROS_BENCH` yardstick (93k events, 20k capabilities).

| Operation | Target |
|---|---|
| `reconcile(mode=call)` no-op | ≤ 5 ms |
| tick | ≤ 50 ms |
| `brief` over 5 records | ≤ 150 ms |
| `tasks()` with 50k task events (warm) | ≤ 10 ms |
| incremental `vault_sync` of one changed capability | ≤ 30 ms |
| vault scan of 10k files (stat only) | ≤ 250 ms (runs in a background thread) |
| `atlas` focus (≤ 300 nodes) | ≤ 80 ms |
| policy decision / append | unchanged: ~20 ms / ~2 ms |

**Data safety for the real vault:**
- Writes only under `<vault>/Research OS/`, atomically and only when content changed.
- Never moves, renames or edits a user or legacy file. Deletes only unedited files it generated (hash-proven).
- The first sync is a dry run that shows N files to be created.
- PDF builds run in scratch directories outside the vault, with the legacy LaTeX lint and shell-escape off.
- Inbox files are referenced in place.
- Run M8 live QA on a **copy** of the 447-file vault first (as LIVE_TEST_1.0 did).

**Decisions taken without asking:**
- Reconcile plus in-process runner, no daemon.
- Manifest outside the vault.
- Path-qualified wikilinks.
- Markdown note is primary and the PDF optional.
- LaTeX → Chromium ladder.
- Legacy notes linked, never edited.
- Version 1.2.0.
- v1.0 decision 5 ("only curated notes; lesson logs stay in the portal") is superseded by the user's request and recorded in the plan doc.

**Open questions for the user only**
1. **Which Obsidian vault, and under which folder?** It is auto-detected from Obsidian's own vault list; the default folder is `Research OS/`. Should generated notes link (read-only) to the existing pre-1.0 notes? The recommended answer is yes.
2. **Which PDF engine is the default when several exist?** MiKTeX/XeLaTeX with the restored STAT303-recitation-style template is the recommendation; Edge/Chrome printing is faster and lighter.
3. **How much does approving an experiment plan authorize?** Either the agent runs every rung of its scale ladder automatically within the plan's stated compute budget (recommended), or only the first rung, with each further rung returning to you for approval.
