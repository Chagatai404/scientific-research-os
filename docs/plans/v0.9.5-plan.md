## 3. Research findings that shape the design

### 3.1 How people actually learn, and what that means for a tutor

- **Retrieval practice and distributed practice rate highest; rereading, highlighting and summarizing rate low** (Dunlosky et al. 2013, *Psychological Science in the Public Interest* 14(1) [verified citation; ratings via press summaries]). Consequence: lecture notes must be *cued recall* material, not a re-readable summary.
- **Learning-styles matching is unsupported** (Pashler et al. 2008, same journal, 9(3) [verified]). Consequence: personalize on **measured performance and knowledge**, never on self-declared "visual/auditory learner". Audio and visuals are added for everyone because of multimedia principles, not to match a style.
- **Multimedia principles** (Mayer): pre-training (introduce key terms before complex material), segmenting, signaling, coherence, modality, redundancy [secondary for the list; confirm wording in Mayer, *Multimedia Learning*, 3rd ed. 2020]. This directly justifies "explain new terms before the lesson uses them" and "narrate a diagram, don't also print the narration".
- **Expertise reversal** (Kalyuga 2007; Sweller et al. 2003 [verified existence, secondary detail]): scaffolding that helps novices hurts experts. The tutor must reduce support as the learner's record improves.
- **Knowledge components** (Koedinger, Corbett, Perfetti 2012, *Cognitive Science* 36(5) [verified]) are the right unit for a learner model. The existing capability graph is already this; terms need the same treatment.
- **AI tutoring can harm without guardrails.** Bastani et al., PNAS 122(26), 2025: ~1,000 Turkish high-school maths students; unguarded GPT help raised practice scores but left students 17% worse once it was removed, while a hint-based tutor avoided the harm [verified via abstract and coverage]. A Harvard physics trial (Kestin et al.) reports about double the learning of an active-learning class [unverified: secondary reports only, effect size not confirmed]. Consequence: the existing rule "an explanation is not understanding" stays, and the tutor should default to hints and learner reconstruction over answers.
- **Scheduling.** FSRS models memory with difficulty, stability and retrievability; MIT-licensed `py-fsrs` (`pip install fsrs`) exists [verified]. Reported savings versus SM-2 vary from about 15% to 50% across blogs [unverified; do not rely on them]. `retention.py` today is evidence-based with adaptive intervals and no named algorithm.

## 4. Target architecture

Principle: **everything the tutor knows or shows is a plain-file record in a registry, derived views are computed, nothing is trusted because it exists.** This is the existing v0.6–v0.9 philosophy; v0.9.5 adds registries rather than a database, service or required dependency. The core stays standard-library Python; every renderer, voice and model is an optional, detected capability that degrades to a simpler route and says so.

```
                        Student model (derived, never stored as truth)
   capability ledger ── term ledger ── learner profile ── retention view
          │                  │               │                  │
          └──────────── context_kernel preflight → "Student Brief" in the receipt
                                   │
   Teaching planner (tutor_plan/tutor_gate) ──► Teaching Card (core idea · terms first · visual · spoken script · retrieval prompt)
                                   │
        ┌───────────┬──────────────┼───────────────┬───────────────┐
   visual registry  resource      animation       narration        lecture note
   (visuals.py;     registry      backend         registry         (vault; layered,
   + diagrams,      (links,       (ManimGX →      (voice.py;        cued-recall)
   molecules,       vetted)       Manim CE →      EN/TR scripts,
   structures)                    keyframes)      pre-rendered audio)
        └───────────┴──────────────┴───────────────┴───────────────┘
                     HTML session runtime (static, offline; clicks load external content)
```

### 4.1 Student model

**Status: S2 implemented (uncommitted)** as `scripts/terms.py` and `references/LEARNER_MODEL.md`: the term ledger (append-only events, states folded per language), glossary, validated profile (learning-style fields refused), measured hint rate and calibration gap, the Student Brief in the receipt (`retrieval.learner.student`, informational: a missing ledger changes no outcome), and the `UNDEFINED_TERM` / `TERM_NOT_RESTATED` / `TERM_UNKNOWN` checks in `tutor_gate.py`. **Deferred from S2:** the `confusable-with` concept relation (it needs ontology validation changes and has no consumer until interleaving exists) and the FSRS-style estimator (waits on your own review history). Events are appended by the tutor after review; nothing records them automatically.

Three derived views over plain records; each is keyed by the same IDs the graph already uses.

1. **Capability ledger** (exists): unknown / learning / demonstrated / retained / fragile / stale, with scope, dimension, context.
2. **Term ledger** (new, `terms/` or frontmatter on concept notes): per term and per language: `unseen → introduced → defined → used → fluent`, where `defined` means the learner restated it and `used` means they applied it correctly without prompting. A term links to the concept(s) that INTRODUCE or ASSUME it, so `tutor_gate.py` can refuse a block that uses an undefined term. This turns the existing terminology gate from a per-question check into persistent knowledge. Language matters: a learner can know "olasılık yoğunluğu" and not "probability density".
3. **Learner profile** (new, small, mostly measured): calibration (confidence versus correctness), hint dependence, typical latency per capability type, preferred language per domain (declared and observed), goals and time budget, misconception history. **No learning-style fields.**

Graph uses (all conservative, none auto-upgrades mastery):
- prerequisite closure picks the next node; failure on a node triggers a probe of its prerequisites, not reteaching the node;
- evidence on a harder node is shown as *supporting* a prerequisite in a separate "propagated" column; it never changes the prerequisite's recorded state;
- a `confusable-with` edge drives interleaving of similar concepts (maximum likelihood estimation versus maximum a posteriori);
- the retention view (existing intervals, optionally an FSRS-style stability estimate) marks what is due; due is advice, not a schedule that runs by itself;
- goal-conditioned frontier (exists) filters what to teach next.

**Student Brief.** `context_kernel.py preflight` gains a bounded section: terms known / shaky / unknown for the target's closure, top misconceptions, calibration, language. The tutor must read it; a missing term ledger degrades the receipt rather than meaning "knows nothing".

Open decision: implement an FSRS-style estimator in the standard library (the formulas are public; default weights are published), or accept the optional `fsrs` package. Recommendation: stdlib estimator with default weights as an advisory view, fitted offline only after enough of your own reviews exist, and compared against the current interval rules on your history before it replaces anything.

### 4.2 Teaching format

**Status: S3 implemented (uncommitted)** — `references/TEACHING_FORMAT.md`; `card` on teaching blocks (shape checked by the gate, rendered by `tutor_gate.expand_cards` as a projection, opt-in per block so existing pages do not change); the word strip as a `glossary` callout built from `introduces` and earlier-block definitions; `scripts/teaching_lint.py` (blocks and notes, warnings only); `assets/obsidian/25_Lecture_Note.md` (L0–L3); theme/vocabulary additions with rebuilt offline bundles. Rendered and inspected at desktop and 375 px width. **Not covered:** the lint cannot judge teaching quality; the spoken script is stored and linted but nothing speaks it until S8; the word strip shows definitions the lesson itself carries, not definitions fetched from the term ledger.

Long paragraphs fail Mayer's segmenting, coherence and redundancy principles. A **Teaching Card** replaces them as the unit of a block:

1. **Core idea**: at most two sentences, no undefined term.
2. **Terms first**: a small glossary strip for every term the card ASSUMES that the term ledger does not mark `defined`, in the learner's language with the other language alongside.
3. **One visual** for one idea (existing cadence), declared with what to notice.
4. **Spoken script**: a separate text written to be heard (no LaTeX, symbols verbalized, term pronunciations marked). The screen shows the diagram; the voice carries the explanation.
5. **Predict-first prompt**, then reveal, then **one retrieval prompt**.
6. Depth on demand: "why", derivation and rigor are collapsible, not default.

A deterministic **teaching lint** (`scripts/teaching_lint.py`) checks the mechanical parts: undefined term before use, paragraph and formula budgets, missing visual or exception line, missing spoken script, a formula before its words. It cannot judge teaching quality and says so.

**Lecture notes for instant recall.** Vault notes keep full lecture content but are layered: L0 gist (one line) and recall cues; L1 "core in 60 seconds" written as questions with the answer in a collapsed callout; L2 lecture; L3 derivation and sources. The first screen of a note is for retrieval, not rereading. Notes link up the graph (`up`, prerequisites) and to their terms.

### 4.4 Animation backend

An `animation` capability sits behind `science-visualize`, selected by detection, never by installation:

1. **ManimGX**: fast iteration, `inspect` for storyboard and layout checks, no LaTeX needed.
2. **Manim Community**: the compatibility baseline and plugin host (`manim-slides`, `manim-voiceover`, `manim-chemistry`, `ManimML`).
3. **Motion Canvas / Remotion**: non-mathematical or presentation motion.
4. **Key-frame panels**: the honest fallback already in the protocol.

Scenes are written once against the CE API. A thin `scripts/animate.py` wraps `render`, `inspect` and `keyframes`, writes MP4, a poster frame, a key-frame strip, the narration script and a basis record, and registers the result in the visual registry with `mode: animation`. Every existing animation rule stays (stated equations, no fabricated physics, editorial versus scientific motion, replay and key-frame companion). A teaching animation follows predict → play → pause → explain, using `manim-slides` where available.

Cautions: v0.1.1 and vendor-only speed claims; Python 3.13+; GPL wheels matter if the app is ever distributed. Acceptance is empirical: in an isolated environment, port three representative scenes (a 2D derivation, a 3D surface, a Typst/LaTeX-heavy equation scene), compare render time and output with Manim CE **on this machine**, and record what breaks.

**Status: S7 implemented.** `scripts/animate.py` (standard library only) detects ManimGX and Manim Community in named virtual environments (`--env` or `RESEARCH_OS_ANIMATION_ENVS`) without installing anything, validates an `animation_schema: 1` spec (a `basis` is required unless the animation is a schematic), lints the scene (network, process and `eval` escapes refused; this is a screen, not a sandbox), renders through ManimGX (`inspect` first, so layout problems stop the render) or Manim Community, takes a poster frame and a six-frame strip with ffmpeg, and registers the result at `rendered` with a `.render.json` of what ran. With no backend it returns an honest unrendered result (exit 3). Slides: Manim Community plus `manim-slides` converts to one offline HTML file; ManimGX presents sections interactively (`animate.py present` prints the command, never runs it). ### 4.5 Scientific diagrams, geometry, physics, chemistry, biology

Separate **what is drawn** from **how it is drawn**. A diagram is a declarative spec (JSON) that a renderer turns into SVG or an interactive view; the spec carries the quantities, so they can be checked independently of the picture.

| Domain | Spec carries | Renderer (optional capability) | Checks added to `scientific_verify.py` |
|---|---|---|---|
| 2D geometry | points, constraints, labels | stdlib SVG generator (exact coordinates), JSXGraph or TikZ for rich output | `geometry-constraint` (angle sums, lengths, incidence, recomputed from coordinates) |
| 3D geometry | meshes, coordinates, camera | PyVista (static), three.js (interactive, vendored offline) | coordinate-frame and unit declarations; bounding-box and orientation sanity |
| Physics models | equations, parameters, units, regime | Matplotlib/Plotly, TikZ (circuit, Feynman, 3D), PhET links for interactive | existing `dimensional`, `regime-match`, `evaluate`, `limit` |
| Chemistry | SMILES/InChI or formula, stoichiometry, mechanism arrows | RDKit (2D depiction), 3Dmol.js (3D), ChemFig/TikZ | `formula-balance` (atom and charge conservation, stdlib parser), valence and molecular mass via RDKit when present |
| Biology | PDB/UniProt/GenBank ids, pathway nodes and edges, sequences | Mol\* or 3Dmol.js (structures), Graphviz/Mermaid (pathways), vetted icon sets | `structure-source` (id resolves, chain and residue range match the claim), `sequence-check` (alphabet, reverse complement, translation by the standard codon table, stdlib) |

A schematic stays labelled *schematic, not to scale*; a structure drawn from a database states its identifier and version; an icon-based biological schematic never implies quantitative fidelity. Generated images remain `candidate → rendered → inspected → verified` under the existing tiers. Blender (already connected to this environment through an MCP server) is an optional route for high-fidelity 3D stills, never the source of a quantitative claim.

### 4.7 Library indexes with links

Two problems: the generator emits no links, and hand-written indexes were never required to.

**Status: S1 implemented (uncommitted) as `scripts/library_index.py`; nothing has been written to your library or vault.** It is a separate module rather than `paper_library.py` subcommands because that CLI is a single-mode `--input` command and subcommands would break existing use. `paper_library.py --apply` now also refreshes `INDEX.md`.

- `library_index.py index --root <library>` renders `INDEX.md` (and per-concept indexes). Every row has title, authors, year, screening and `read_depth`, plus links **built deterministically from identifiers**: DOI → `https://doi.org/<doi>`, arXiv → `https://arxiv.org/abs/<id>`, `source_url`, and the local PDF as a vault wikilink or `file:///` path. No network is needed to build them.
- A row with no identifier carries an explicit `no identifier` marker; a link is never guessed.
- `library_index.py lint <file>` fails on any row without a link or marker. The scout's candidate contract already requires an HTTPS `source_url`, so scout output can always be linked. A literature session is not complete until its index lints clean: written as a rule in `PAPER_LIBRARY.md`, **not yet enforced by `tasks.py`** (a later change, if you want it).
- Optional `--verify-links` makes HEAD requests, separately and honouring robots policy; a dead link is reported, not deleted.
- **Backfill** touches your library and vault notes, so it needs your go-ahead. Derivable links only: arXiv ids in filenames (for example `1803.11173v1`), Elsevier `1-s2.0-S…-main.pdf` PII to a ScienceDirect URL, DOIs already in metadata. Publisher-style names such as `s41605-021-00267-4` do not determine a DOI (Springer journals of this form appear under both `10.1007` and `10.1038`), so they get the `no identifier` marker; a first draft of the tool guessed `10.1038` and was caught wrong on real data, so the heuristic was removed.

### 4.8 Voice

Code-switching (English terms inside Turkish sentences) is marked per span so the engine can switch voice or phonemes.

### 4.9 Code comprehension: teaching the code that was written (S3C)

The Research OS asks the researcher to own the concepts; it must ask the same of the code. The need is documented: in a randomized
trial of 52 mostly junior developers learning an unfamiliar Python library, those who used an AI assistant scored about 50% on a
follow-up comprehension quiz against about 67% for hand-coders, with the largest gap on debugging; speed gains were not significant.
Learners who delegated fully scored worst (24–39%), and those who generated code and then asked specific follow-up questions kept
their learning (65–86%) (Shen and Tamkin 2026, arXiv 2601.20245; **[secondary]**: abstract and Anthropic's summary read, statistics not
checked; small sample, which the authors say). Reading and tracing code are also known to be fragile skills that other programming
skills depend on (Lister et al. 2004, *ACM SIGCSE Bulletin* 36(4) **[verified citation]**).

**Status: S3C implemented (uncommitted)** — `references/CODE_LEARNING_PROTOCOL.md`; `skills/code-walkthrough/`; `scripts/code_walkthrough.py` (`units`, `locate`, `verify`, `trace`, `map`, `levels`, `ownership-gaps`, `blocks`); the read-only `walkthrough-verifier` agent; kernel workflow `code-walkthrough`; `checkpoint_pace` in the learner profile. Default-on for consequential units, with a recorded skip becoming an open ownership gap, is built as decided. **Verified by 23 tests** against throwaway git repositories: units and touched symbols, the secrets denylist, locators (including commit-pinned ones), stale, forged, missing and out-of-range locators, unexecuted and contradicted claims, `trace` refusing unapproved commands and doing nothing on a dry run, the dependency-ordered map with cycles, proposed gaps without a `selection`, and installation for both providers. **Not covered, stated plainly:** `verify` shows cited lines exist and match, not that the explanation is right; the risk class is a name-based proposal, so a consequential change under an innocuous name is missed until the researcher confirms classes; `map` reads Python imports only (other languages need the code graph); `trace` cannot tell whether a human wrote `approved_commands`, so the protocol forbids agents from writing it; mutation exercises are described in the protocol but have no tool support yet; **decision 8's second half is still open** (whether `trace` and scratch-worktree mutations may run), and until you decide, `trace` is dry-run by default and the verifier agent runs nothing that is not in a record you wrote.

**What vibe-wise is** (github.com/nykooi1/vibe-wise, MIT, a Claude Code and Codex plugin, about 3.7k stars; **[verified from its README]**,
its skill files were not inspected and I found no independent evidence that it improves understanding **[unverified]**). It teaches while
the AI builds: setup asks for experience and preferences; the AI asks for your approach first; **build** checkpoints reason through the
approach, **design** checkpoints record a design ("Confirm and continue"), **implementation** checkpoints authorize one step ("Implement
this step"), each with "Discuss"; after implementing it explains what changed, how the key code works, why it fits your decision, which
tests it added and which checks ran, with small diagrams; extra implementation details it proposes are listed separately with reasons;
a project map, profile and notes live in `.vibe-wise/` and resume across sessions; pacing is Light, Normal or Frequent.

**Decision (2026-10-16): the walkthrough is default-on for consequential units; skipping one records an open ownership gap.**

**What to adopt, adapt and refuse**

| vibe-wise idea | In Research OS | Why it changes |
|---|---|---|
| Ask the user's approach first | **Approach-first prompt** before stage 12 presents a plan: the researcher states how they would build it; the plan is compared with it | attempt before reveal; already the OS's predict-first habit |
| Build / design / implementation checkpoints | Design = the existing stage 12 plan and stage 13 approval, unchanged. "Implement this step" becomes **per-unit** work inside the already-approved scope; it never replaces the plan approval | the research protocol owns build authorization; teaching never bypasses it |
| Post-implementation explanation | **Code Walkthrough** of each change unit, generated from the actual diff and the code graph, every claim carrying a locator (`path`, line range, content hash) that a script re-checks | vibe-wise relies on the AI's own account; the OS requires independent verification |
| Tests and checks reported | The walkthrough records the **executed** command, exit status and output summary; nothing is narrated as having passed | same reason |
| Extra details listed with reasons | **Agent-introduced choices** (library, default, threshold, seed, split, normalization) listed per unit with reason and alternatives; each consequential one is proposed as an ownership gap (`introduced_by`) for the researcher to accept, change or leave open | hidden choices are validity risks as well as learning gaps |
| Project map | **Code Map**: derived from the code graph (structure stays in graphify) plus the research graph's code-file links; the vault holds only a curated note saying which module implements which concept or decision | Graphify for structure, Obsidian for understanding; no duplicated graph |
| Beginner/intermediate/advanced | **Measured**, not declared: the capability ledger's tool and navigation dimensions decide how much scaffolding a unit gets (expertise reversal) | self-assessed level is a weak signal; the ledger already exists |
| Light/Normal/Frequent pacing | Declared `checkpoint_pace` in the learner profile, with a floor: a **consequential** unit (touches data loading, splits, preprocessing, metrics, loss, seeds, geometry or anything a claim depends on) always gets the walkthrough and probes; routine boilerplate may get a summary only | pacing may reduce teaching, never authorization or scientific review |
| Progress notes, no mastery scoring | Viewing a walkthrough is **never** evidence. Evidence comes from the learner's answers to code probes, reviewed against criteria, through the existing ledger | the OS's core rule |

**The loop.** (1) *Existing or inherited code*: map first (`graphify query`), then a guided tour ordered by dependency edges: entry points,
one input traced end to end, then a small modification exercise; produces the Code Map note. (2) *New work*: approach-first, plan with
**change units** (files, purpose, linked concepts, risk class, teaching level) and the agent-introduced choices, human approval, build
unit by unit, **walkthrough after each unit**. (3) *Handover*: consequential units without learner evidence appear as open ownership
gaps; `defense.py ownership` and the viva include code questions; they never block research by default (existing rule) but surface when the
researcher claims personal understanding, presents or modifies the work.

**The walkthrough** is an HTML session built on S3 cards and the existing `implementation` block, whose eight literacy items are already
the right shape (why chosen, assumptions, how it works, how to run, how to verify, where to change it, how it fails, alternatives):
one idea first; code terms in the word strip and the term ledger; a call-flow or data-flow diagram taken from the graph; one input traced
through the real code with each step cited; then probes using the existing kinds `code-comprehension`, `tool-exercise` and
`implementation-task`: predict the output (checked by running it), find the line that would change for a stated requirement, explain a
function back, and "what breaks if this guard is removed?" (answered by running the mutation in a scratch worktree, only with approval).

**Components**: `references/CODE_LEARNING_PROTOCOL.md`; `skills/code-walkthrough/`; `scripts/code_walkthrough.py` with `units` (change units
from `git diff` and the graph, a proposal only), `skeleton` (session blocks with locators and empty literacy fields), `verify` (every
locator exists and its hash matches the commit; a changed file marks the walkthrough stale), `trace` (runs only a command named in the
approved plan or approved on the spot, and records the real output for predict-first questions) and `map` (Code Map proposal);
a read-only `walkthrough-verifier` agent that re-checks consequential claims by reading and running the cited code; kernel workflow
`code-walkthrough` (learning advisory, research and project essential, code advisory); `checkpoint_pace` in the profile; wiring through
`install.py`, `validate.py` and the parity tests as for other roles.

**Guards**: a path denylist (`.env`, keys, credentials) before anything enters a walkthrough or the vault; code excerpts are short with
`path:line` locators, never whole files; no private data is copied into the vault; executing project code is an action under the
research protocol's approval boundary, so `trace` refuses a command that is not in the approved plan or explicitly approved; the
walkthrough text never says "verified" for what only the author asserted.

**Honest limits**: a clean `verify` shows the cited lines exist and match, not that the explanation of them is right (the reviewer agent
and the learner's own probes address that); mutation exercises need a working test environment; nothing here measures that the
researcher understands the code, only that they answered probes.
