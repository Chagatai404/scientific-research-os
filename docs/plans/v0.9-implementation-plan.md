## Architecture and prior decisions

Reviewed v0.7/v0.8 implementation records, v0.8.5 HTML plan, HTML design record,
v0.8.6/v0.8.7 changelog, canonical parsers, installation and regression infrastructure.
Work happens on a clean branch of `main`; other worktrees (Codex's `.codex/worktrees/*`)
are not modified. No user research or learning data is changed: tests use temporary
vaults and synthetic fixtures only.

Preserve five authorities: capability ledgers, research records, code, paper catalog,
and session state. Reuse `knowledge.discover/query`, `research.validate/enrich/context`,
`tutor_plan.plan`, `tutor_contract`, `tutor_session.replay`, `paper_library.catalog/match`,
EvidenceAtoms and computational manifests. Rendering, context receipts and verification
reports are projections/artifacts, never replacement authorities.

The new context service will expose versioned requests/receipts, source fingerprints,
bounded explicit relationships and failure diagnostics. Workflow entrypoints must
validate receipts before dependent operations. New-session bootstrap must not depend
on session existence. Essential unavailable context blocks dependent actions; genuinely
empty readable roots remain distinguishable. Provider adapters share this contract.

EvidenceAtom already recomputes finite Decimal sum/product/ratio
(`validate_evidence.py:155–217`) with input fingerprints and value/unit bindings.
Reuse that mechanism; the gap is richer calculations, dimensional algebra and scoped
independent verification, not an absence of all executable arithmetic.
Verification will execute bounded reviewed calculations and record input assumptions,
environment, tolerances and unresolved obligations in computational provenance. A
successful process or structurally valid manifest is not scientific verification.
Neither majority agreement nor optional-library absence settles a scientific claim.

## Slice 1 record: Context Kernel (implemented)

`scripts/context_kernel.py` (stdlib, read-only) retrieves a bounded subgraph over the learning graph,
research graph, project note, code graph, paper library, visual registry and earlier sessions, and writes a
schema-1 receipt: per-source status (`ok / empty / missing / invalid / unavailable / not-configured /
not-applicable`), content fingerprints, truncation flags, limitations and a tamper-evident `receipt_id`.
Contract: `references/CONTEXT_PROTOCOL.md` (a test keeps its workflow table equal to `POLICY`).

Enforced, not advised: `html_sessions.py create` runs the preflight and refuses (exit 2, nothing written) when
essential context is blocked; `add_question`, `append_session` and `review_response` (with new teaching) require the
bound context to be current, rebuilding a stale binding and refusing a blocked one; `tasks.py` stages 7, 8, 14, 15
require one fresh `context-receipt` input. Historical sessions without a binding keep working and can be adopted
with `html_sessions.py context SESSION --bind`. The Obsidian host keeps the binding (local paths) out of the page.
`session_context` is now a thin caller and works before the session exists (complaint 7 test repaired).

Known limitations: the receipt proves what was consulted and that it is unchanged, not that a model understood it;
only the gated actions make skipping it fail. Freshness fingerprints whole source trees (cheap stat digest first);
visuals and earlier-session scans are advisory and not fingerprinted. Stage 3 literature discovery is deliberately
ungated (neutral discovery). Live provider omission rates remain live-only.

## Slice 2 record: Scientific Verification Engine (implemented)

`scripts/scientific_verify.py` (stdlib core; sympy, numpy, scipy, mpmath and statsmodels are optional independent
cross-checks, never required; pint/astropy absent here so a small SI dimension algebra is built in). A spec lists a
claim, its declared assumptions/domain/tolerance and executable *checks*; the engine runs them and records a scoped
outcome. It never "verifies" free text: claims without executable obligations are `not-checked`, and a missing
obligation is reported as unresolved, never silently upgraded. Expressions are parsed from a whitelisted AST and
interpreted (no `eval`, no `sympify`). Outcomes: `verified-in-scope`, `partially-verified`, `invalidated`,
`unresolved`, `not-checked`. Any failed check invalidates; an unavailable optional tool downgrades only when the
check was required and never invalidates; consequential claims need two independent method families and a valid
context receipt. Records (`*.verification.json`, schema 1) embed environment/versions and are re-runnable
(`rerun` reproduces the outcome). Linked to existing evidence by listing the record in a manifest's `artifacts`
and a research record's `artifacts`; `research.py` reports their outcome. Check kinds: evaluate, equivalent,
integral, derivative, limit, dimensional, rate-interval (exact Clopper-Pearson), propagation (with covariance),
resampling-unit, fit-partition, assumption-declared, regime-match, mapping-declared.

Delivered: `scripts/scientific_verify.py`, `references/VERIFICATION_PROTOCOL.md`, `agents/mathematics-reviewer.md`
(new) and strengthened statistics/physics reviewers (three distinct read-only roles, each bound to its context
workflow and required to list what it did **not** verify). The protocol is bundled into seven reviewer roles for both
providers and the engine ships in every installed skill. `research.py` reports linked `*.verification.json` outcomes
beside the evidence and the context kernel retrieves them. 44-case regression fixture (general + AMS ECAL).

Honesty rules that are tested: any failed check invalidates; an unmet required obligation lowers the outcome and is
listed; an unavailable optional library never invalidates or downgrades a correct result; floating-point disagreement
inside the expressions' own running-error bound is not a refutation (adjudicated at high precision, else
`unresolved`); a consequential claim needs two independent method classes (or a second formulation), a
`bounded`/`qualified` reviewer and a fresh review-workflow context receipt, else it stops at `partially-verified`
or is refused. Real defects found by writing the tests: a limit and an identity that naive floating point wrongly
refuted (cancellation); a flag/field name collision (`required`); an unhandled exception type that would have
crashed research-graph loading on a corrupt record.

Known limitations: it checks *structured obligations only* - prose claims without executable checks are
`not-checked`, and `resampling-unit`, `fit-partition`, `regime-match` and `mapping-declared` trust the declared
description of a pipeline rather than inspecting code. No proofs (a theorem needs a proof assistant). Dimensional
algebra covers SI plus a small unit table (unknown unit = error). Exact intervals are binomial only. Independence
classes are coarse. Whether live reviewers write good specs is live-only.

## Slice 3 record: scientific rendering (implemented)

Root cause: inline text went through a regular-expression renderer (`_inline`) that could not nest emphasis, knew only
`$...$`, and the runtime built every question surface with `textContent`, so prompts, options, hints, explanations,
feedback and open questions never rendered mathematics or formatting at all.

Decision (no Mistune vendoring: smaller dependency/installer surface, no upstream math-escaping advisory, and one
grammar we control): `scripts/rich_text.py` and `assets/html-runtime/richtext.js` implement one grammar twice - a
single scan that extracts atomic tokens (code, TeX in four delimiter styles, links, tags) then resolves emphasis with
the CommonMark delimiter-stack algorithm - held identical by `tests/fixtures/richtext-cases.json` (63 cases). Display
math supports `$$`, `\[ \]` and bare math environments; labelled equations are numbered (`{#eq:name}` / `\label`) and
cited with `\eqref` / `[@eq:name]`, forward or backward. Unsupported syntax stays visible as authored with a
diagnostic (the runtime now restores the exact authored source, delimiters included, when KaTeX rejects TeX).
Question text uses the same grammar in the static HTML and in the runtime; `<option>` text and accessible names use
the plain form. The runtime builds DOM with `createElement`/`textContent` only.

Defects found by the tests: nested emphasis stacked thousands deep exhausted the Python stack (now capped identically
in both implementations); a stale bundle is now a test failure (`richtext-conformance.js` checks `session.js` contains
the exact sources); the DOM builder and serializer disagreed on attribute order for display math in a paragraph.

Verified in real Chromium on both the standalone page and the production host path (sanitizer + sandboxed iframe),
light and dark: lesson text, display/aligned/matrix equations, equation numbers and references, prompts, options, hints,
explanations, tutor feedback, open-question history, plus hostile-text inertness and DOM-equals-recorded-HTML for
every corpus case. Screenshots were inspected.

Compatibility: generated HTML of sessions using affected constructs changes; refresh with
`html_sessions.py refresh-projection` (canonical Markdown/state untouched, old HTML backed up). The sanitizer allowlist
gained `del`.

Known limitations: wikilinks are still inert spans (Slice 5); figure/widget placement was still appended here (repaired in Slice 4);
footnotes, raw HTML other than `sub/sup/mark/br`, and Pandoc `~sub~`/`^sup^` are deliberately unsupported; the
Obsidian *reading view* of the Markdown bridge is unchanged (it uses Obsidian's own renderer); real Obsidian desktop
rendering is not claimed.

## Slice 4 record: inline visuals and Excalidraw linkage (implemented)

Root cause (complaint 3): the page had no notion of *where* a visual goes. Widgets were appended after the content
(`_widgets_html`), unmatched images were appended by `export_session` and by the Obsidian companion's
`sanitizeHtml`, and nothing recorded what kind of evidence a figure was or tied a drawing to its viewable export.

Decision: placement is a per-session contract, not a global behaviour change. New sessions record
`placement: explicit`; a figure is `![alt](resource:ID "caption")`, a widget is `<!-- ros-widget: ID -->`, both in the
lesson text. For such sessions nothing is appended: a declared-but-unplaced visual, a placeholder with no declaration
and a double placement are rendered as visible `aside.ros-diagnostic` notes (with the command that fixes them) and
reported by `validate`. Sessions without the field keep v0.8.7 behaviour exactly (so no historical page changes).
`html_sessions.py place` writes the marker at an exact, unambiguous position (heading, unique phrase or end), refuses
guessing, requires alt text, never places twice and preserves line endings, fenced code and frontmatter.

One drawing is one visual with two files: `scripts/visual_assets.py` renders an Excalidraw scene (the editable source) and
an SVG export from that same scene, linked in the registry record (`exports`, `source_sha256`, `spec_sha256`).
`visuals.visual_class(record)` derives the on-page evidence label from the record (schematic / analytic / empirical /
source), so a lesson cannot relabel a schematic as data; model-driven and data-derived figures also show their linked
verification record's outcome (re-validated by digest at attach time) or "not independently verified". SVG is accepted
only as static drawing (allowlist; no script, foreignObject, animation, handlers, outside references, DOCTYPE; 1 MiB)
and is checked on attach, save, export and in the companion plugin (`svgProblems` in `main.js`, mirrored rules).

Files: `scripts/visual_assets.py` (new), `scripts/html_sessions.py` (placement, `placements`, `place`/`attach-visual`
CLI, SVG checks), `scripts/visuals.py` (schema 1 optional fields), `extensions/obsidian-html/main.js`,
`assets/html-runtime/theme.css` (+ rebuilt bundle), `references/VISUALIZATION_PROTOCOL.md`,
`references/HTML_SESSION_PROTOCOL.md`, `skills/visualize/SKILL.md`, installer helper lists, `scripts/release_gates.py`.
Tests: `tests/test_visual_assets.py` (28), baseline placement tests no longer expected failures, `html-host.test.js`
(SVG and resource markers), `html-visuals-browser.cjs` (real Chromium, standalone + production host path, light/dark,
phone width, hostile SVG inert) with `support_visual_session.py`.

Compatibility: schema-1 visual records gain optional fields only; sessions without `placement` are untouched; the
companion plugin's `sanitizeHtml` gained an optional fifth argument whose default keeps the old behaviour.
Decision (checked, not assumed): only `create_session` stamps `placement: explicit`. `migrate` builds its own state and
`import_bridge`/`refresh-projection` re-save an existing one, so converted and historical sessions stay legacy; migration
produces no widgets or resources in any case. The only production callers of `create_session` (`html_sessions.py create`,
`vault.py`) pass neither `widgets=` nor `resources=`, and no skill or agent prose tells an agent to declare one without
placing it (`docs/HTML_SESSIONS.md`'s API example now shows the marker). Hardening after review: processing instructions

The Slice 4 gate run below executed against `482bb69`; the hardening commit was re-verified with the visual-asset unit

Known limitations: the SVG export is drawn from the scene geometry in a clean style (supported element types:
rectangle, ellipse, diamond, line, arrow, text; others are reported, not drawn) and is not byte-identical to the
Excalidraw plugin's own export; a drawing saved in the plugin's compressed form is reported and must be decompressed
first; nothing was exercised inside real Obsidian or with the installed Excalidraw plugin (only file-based detection).
Computed plots are attached from registered files; Research OS does not generate plots from equations in this slice.

## Slice 5 record: navigation and session workspace (implemented)

Root cause (complaints 5, 6, 10): section titles came from authors and from the shipped templates themselves
(`### Node 1 — `, `### Step 1 — ` rendered as headings when left unfilled); wikilinks were inert `<span>`s; the open-question
composer and history sat at the bottom of a long page (reachable only by scrolling), with no link back to the concept being
read; and nothing told a learner where they were, what came before, or let them leave and return.

Decision: navigation is a validated *host* operation, never an href or filesystem access from the page.
- `[[Note]]` (and entries of a new `navigation` state field) render as links that post a typed `navigate` request. The host
  (`main.js`) re-validates the reference itself (same rule in Python, the runtime and the host, pinned by
  `tests/fixtures/note-targets.json`), refuses anything the session does not itself link to, resolves it with
  `metadataCache.getFirstLinkpathDest` (no note is ever created), rejects non-note and hidden-path files, throttles requests,
  and opens it with `workspace.openLinkText(..., 'tab')` - a new tab, so the lesson keeps its exact position. A standalone page
  says it cannot open notes, beside the link. Malformed targets stay visible and are not links.
- The host remembers the reading position in memory and hands it to a rebuilt page; open questions record the section they
  were asked in (`origin`, validated in Python and the host) and the panel returns the learner there.
- Three areas: contents rail (hierarchy, current section, per-section progress, previous/next, "Where am I?", related notes),
  lesson, and a questions panel (history with Open/Answered, responses waiting for the tutor, new-answer signal). From 1600px
  all three are visible; below that the contents bar is sticky (a defect found by the test: "Where am I?" was unreachable
  without scrolling away) and the panel is a drawer (Escape closes, focus returns, phone width fits). Panel and nav titles are
  labelled landmarks, not headings, so the page still adds no headings of its own.
- Titles: `heading_issues` flags workflow-position/identifier headings and unfilled template placeholders; `validate` reports them
  for sessions created by v0.9; a session without a title is named by its shallowest meaningful heading; the templates now use
  `[Name the concept this part teaches]` / `[Name what this step achieves]`.
- `html_sessions.py navigation <session> [--apply]` derives prerequisites, first/recent earlier lessons and research
  applications from the context kernel's receipt (dry run by default); missing sources contribute nothing.

Files: `scripts/html_sessions.py`, `scripts/rich_text.py`, `assets/html-runtime/{runtime.js,richtext.js,theme.css}` (+ rebuilt
bundle), `extensions/obsidian-html/main.js`, `assets/obsidian/{00_Tutor_Session,02_Derivation}.md`, protocol docs, tests
(`test_session_navigation.py`, `html-workspace-browser.cjs` with `support_workspace_session.py`, host/conformance/baseline
updates; the existing browser tests now open the questions panel before using it, an intended behaviour change).

Compatibility: sessions without `placement` keep every earlier behaviour except that wikilinks to valid targets are now links;
the open-question composer moved into the panel (tests and any automation that typed into it must open the panel first);
`ROS_HOST` gained an optional `position`. Historical sessions are not held to the title rules.

Known limitations: the Obsidian side (`getFirstLinkpathDest`, `openLinkText(..., 'tab')`) is exercised against a faithful mock of
the documented API, not inside real Obsidian; related-note targets are note names resolved like wikilinks, so two notes with the
same name resolve as Obsidian would; reading position is held in the host's memory only (lost when Obsidian restarts); the
"Where am I?" breadcrumb reflects the section in view.

## Slice 6 record: concept-first tutoring gates (implemented)

Root cause (complaint 4 and the tutoring half of 9): the concept-first rules lived only in skill prose. The canonical
TESTS/ASSUMES/INTRODUCES contract, scoped probes and the diagnostic budget existed in `tutor_contract.py` and
`tutor_session.py`, but the live HTML questions were not connected to them, nothing checked what a section assumed against
what the learner is recorded as knowing, an explanation request had no representation, and an HTML review recorded a bare
verdict with no criteria, assistance or reviewer.

Decision: an opt-in, executable layer, `scripts/tutor_gate.py`, over declared structure. It never grades, writes a ledger or
infers mastery.
- **Prerequisite introduction gate.** A session declares `teaching` blocks (`heading` must match exactly one lesson heading;
  `kind`, `target`, `assumes`, `introduces`). `tutor_gate.py check` compares each block's `assumes` with the learner view (a
  context receipt or `{id: state}`): established means demonstrated/retained and fresh; weak, stale, in-progress and absent are
  not. A dependency is satisfied only by the learner's record or an *earlier* block that teaches it (`explained-earlier`,
  which leaves the record unchanged: unknown mastery stays unknown). Otherwise `UNSUPPORTED_PREREQUISITE`, with the options
  teach / probe / branch. An application block needs its concept taught or established first
  (`APPLICATION_BEFORE_CONCEPT`); a question may assume only what is established, explained earlier in the lesson, or
  defined by its own `INTRODUCES`.
- **Probe contracts.** A question's `contract` is checked with the existing `tutor_contract.scoped_question_issues` and the
  knowledge model's dimension/method rules, plus: one capability, method consistent with the question format, units 1..8,
  a probe kind from the ten the brief names, explicit criteria for any answer someone must review, and the diagnostic budget
  (default 5; only a recorded learner request extends it). Multiple-choice cue heuristics (few/duplicate options, catch-all,
  length cue, absolute-word cue) are warnings, honestly labelled as heuristics. `add-question` rejects a malformed contract.
- **Adaptive explanations.** Nine learner requests (simpler, rigorous, derivation, visual, analogy, worked example, physical
  meaning, implementation, prerequisites) are a new `explanation-request` event with an `origin`, saved as
  `explanation_requests`, listed in `pending_activity`, answered by `answer-explanation` (links to a real heading) and shown
  in the questions panel with a way to the explanation and back. Python and the host refuse unknown modes, a question id, any
  credit field or a malformed origin; a request never alters `evidence_proposal`.
- **Evidence.** `review` takes `criteria_met` (one per declared criterion; required when the question declares criteria; a
  `correct` verdict needs all) and `reviewed_by`. `evidence_proposal` assembles the actual response, criteria and which were
  met, scope/dimension/method, hints used, solution shown first, reviewed outcome, transfer, and retention `not-assessed`; it
  is a proposal for a human, `counts_as_independent_demonstration` requires reviewed pass, no assistance and a method that
  reconstructs (recognition may stand only for recognition). Nothing is written.
- **Implementation literacy.** An `implementation` block must carry eight items (why chosen, assumptions, how it works, how to
  run, how to verify, where to change it with code locations, failure modes, alternatives); declaring them also renders them
  under the heading (the stored Markdown is untouched), so they are taught, not just claimed.

Acceptance with a simulated learner (known gaps: one unknown, one in-progress, one weak, one stale prerequisite): advanced
material is blocked until each dependency is addressed; teaching it first unblocks while leaving mastery unknown; the same
checks run as `tutor_gate.py check` with an exit status. Interruption, misconception correction, independent transfer, answer
review and retention recording are exercised through the canonical `tutor_session.replay` (3 reviewed answers, branch returned
to the original question, budget enforced, no ledger/mastery output) and `evidence_proposal` (retention `not-assessed`).

Files: `scripts/tutor_gate.py` (new), `scripts/html_sessions.py`, `extensions/obsidian-html/main.js`,
`assets/html-runtime/{runtime.js,theme.css}` (+ bundle), `references/TUTORING_GATES.md` (new), HTML session protocol, tutor and
course-study skills, installer helper lists; tests `test_tutor_gate.py` (36), the workspace browser test (explanation
requests live, end to end) and the host Node test.

Compatibility: all new state fields are optional and a session that declares nothing is untouched; `review_response` and the
`review` CLI gained optional arguments; the `explanation-request` event type is new in both the Python and host validators
(an older host would reject it, so update the companion with the scripts).

Known limitations: the gate checks declared structure, not the wording of the lesson (it cannot tell whether a term was
defined before use in prose, only that the block declares its definitions); MCQ distractor plausibility needs a human; the
learner view depends on the context receipt's node ids matching the concept/capability ids a block names (a mismatch reads as
unknown, which is the safe direction); evidence proposals are not yet turned into ledger rows automatically, by design.

## Slice 7 record: durable tutoring supervision (implemented)

Root cause (complaint 9): `wait_for_activity` treated an unreadable session as idle and a timeout as the end of listening,
`pending_activity` showed only the latest submission per question so an earlier unreviewed answer vanished from the agent's
view, nothing recorded whether an agent was still there, and the page showed "Checking…" whether or not anyone was
checking. A latent Slice 6 defect surfaced during the recon: `render_context` would have raised `KeyError` on a pending
explanation request.

Decision: three kinds of fact, kept apart (`scripts/supervision.py`).
- **Pending work is derived from the saved session** and therefore survives a timeout, a crash and a restart. Every unreviewed
  submission is its own item (`attempt` n of N, with the hints and solution shown before *that* submission). A review names the
  response it judges and records, explicitly, which earlier attempts it supersedes (`covers`); nothing is dropped silently.
  Repeating a review is idempotent. `render_context` and `pending_activity` know every kind (response, open question,
  explanation request).
- **Liveness is a lease**, a small sidecar `<session>.supervision.json` that an agent renews while it listens or reviews
  (`wait --holder`, or `supervision.py heartbeat`) and that expires by itself (15..3600s). It is validated with the same
  shape in Python and the host, written atomically, never counted alive when malformed or unreadable, and two live agents never
  share a session (`LEASE_HELD`, `--takeover` is deliberate). A wait that finds work moves the lease to *reviewing* those
  submissions. A wait that times out changes nothing in the session and leaves the lease to lapse, so the page then says
  disconnected. No provider is claimed to persist after its process ends; resuming means a new agent reads the saved state.
- **Explicit decisions** are saved with a reason and a bounded history: paused, failed (recoverable; needs a reason),
  completed (refused with `PENDING_WORK` while any submission awaits review; reopening a completed session needs a reason).

The page derives one of eight states (active, waiting for learner, response awaiting review, agent reviewing, paused,
disconnected, completed, failed-recoverable) with the same function in Python and the runtime, pinned by
`tests/fixtures/supervision-cases.json` (16 cases covering every state). The host reads the lease (polling every 5s, since
Obsidian does not announce changes to it), forwards it with its own clock, and the page re-evaluates expiry itself every 3s,
so a tutor that vanishes is shown as disconnected without anyone telling the page. "Checking…" is shown only while a live
lease exists; otherwise the response reads "Saved, waiting for the tutor". `wait` on an unreadable session now returns an
error instead of idle. A defect found by the browser test: a withdrawn `supervision` record lingered on the page through a
merge; the host now always sends the field.

Acceptance: a submitted response survives a timeout and a simulated process interruption (a lease that lapses with no release,
and a save interrupted mid-review recovered with `resume --apply` without loss or duplication); a new agent resumes from
persisted state alone; the UI tells waiting from disconnected, including a lease that runs out on its own; no answer is marked
complete or lost (completion is refused while work is pending; a submission made while disconnected is saved and shown as
waiting).

Files: `scripts/supervision.py` (new), `scripts/html_sessions.py`, `extensions/obsidian-html/main.js`,
`assets/html-runtime/{runtime.js,theme.css}` (+ bundle), HTML session protocol and tutor skill, installer helper lists;
tests `test_supervision.py` (25), the shared fixture, `html-supervision-browser.cjs` (real Chromium), host and runtime-unit
Node tests; the two Slice 7 baseline expected failures removed and one earlier assertion corrected (an old expectation
encoded the hidden-submission defect).

Compatibility: `pending_activity` returns one item per unreviewed submission (it used to return the latest only) and items gain
`attempt`; reviews may carry `covers`, `criteria_met`, `reviewed_by`; the state may carry `supervision`; the host forwards
`supervision_live`/`host_now`. The existing tutor browser harness now supplies a live lease, because "Checking…" without a

Known limitations: nothing here can start, keep alive or restart a provider process (that is deliberate and stated); liveness

## Slice 8 record: library-aware literature scouting (implemented)

Root cause (complaint 8): `literature_check.check` examines only the papers a manifest supplies and nothing called the local
`catalog`, so a scout could not know what the library held; the catalog stored no record of how much of a paper was read; a
damaged library made any read raise; and nothing separated discovery from reconciliation, so the same agent that saw the
project's preferences also chose what to search for.

Decision: a five-step chain with a different party at each step (`scripts/scout.py`, protocol
`references/LITERATURE_SCOUTING.md`).
- **Inventory** is read-only and tolerant (`paper_library.inventory/scan/fingerprint`): it takes no lock, writes nothing, and
  *reports* unreadable records and one identifier on two records instead of failing or repairing. A receipt records the catalog
  fingerprint and its own tamper-evident identity, or states `configured: false`; a changed library makes it stale.
- **Discovery** receives a neutral brief (question, facets, required searches) that contains nothing from the library, the
  project or the implementation. Its report must declare what context it actually saw, run a search of every required kind
  (a hypothesis-sensitive question needs `competing`, `null-result` and `validity-limits` as well as `primary` and `review`),
  and return only unverified candidates whose claim locators cannot point deeper than the material actually read.
- **Reconciliation** labels each candidate (already collected / newly discovered / duplicate / previously rejected / ambiguous
  identity / conflicting identifiers / unidentifiable / not checked), reports the library's PDF state and read depth beside
  the scout's, and proposes integration (`executed: false`). It refuses a stale inventory and an invalid report.
- **Verification handoff** carries identity, source and claims with locators and nothing else (no relevance, label, tags or
  screening).
- **Executable order**: `tasks.py` blocks a stage-7 reconciliation task without exactly one intact, current `library-inventory`
  input (`INVENTORY_REQUIRED/INVALID/STALE`) and a stage-3 discovery task that carries one (`DISCOVERY_NOT_NEUTRAL`).

Behaviour now working: a scout pass starts from an inventory; already-collected and previously-rejected papers are recognised
across DOI/arXiv/title variants; ambiguity is surfaced for a person; a collected PDF is distinguished from a read paper
(`read_depth`, which deepens and never regresses); discovery cannot be a search for support only; the verifier packet cannot
tell the verifier what the answer is expected to be.

Files: `scripts/scout.py` (new), `scripts/paper_library.py` (`read_depth`, `scan`, `fingerprint`, `identity`, `inventory`;
`_record` extracted from `catalog`, whose strict behaviour is unchanged), `scripts/tasks.py` (kind + gate), `scripts/install.py`
(helper lists), `references/LITERATURE_SCOUTING.md` (new), `references/PAPER_LIBRARY.md`, `agents/literature-scout.md`,
`skills/research-session/SKILL.md`; tests `test_scout.py` (34), seven new gate tests in `test_tasks.py`, and the Slice 8
baseline `expectedFailure` removed.

Compatibility: `read_depth` is an optional manifest field; existing records, paper IDs and ingestion are unchanged; `tasks.py`
gains one binding kind and the stage-7 requirement (existing stage-7 tests now bind an inventory receipt, which is the point:
reconciliation without an inventory is exactly what is no longer allowed).

Known limitations: nothing searches the web or calls a provider (live scout behaviour is a provider test, not claimed here);
neutrality of discovery is the brief's contents plus the scout's declaration, not proof; the task gate checks a receipt against
the library root the receipt itself recorded; a library moved or re-rooted after the receipt reads as stale by design; reading
depth is a record of effort and says nothing about understanding or correctness.

## Slice 9 record: Obsidian plugin integrations (implemented)

Root cause (complaint 4, with Slice 4): plugin detection was scattered (one function for Excalidraw, prose for the rest), nothing said
whether a plugin was enabled, damaged or too new for the running Obsidian, and only the plugins that had been installed in v0.6 were
considered at all. The v0.6 documents also described Breadcrumbs as having a single "explicit edges only" switch, which Breadcrumbs 4
does not have.

Decision: one read-only detector, a registry that states what each adapter may and may not establish, and a built-in route for every
use case, so a plugin only ever improves a job that already works without it.
- **Detection** (`scripts/obsidian_plugins.py`): reads `community-plugins.json`, `core-plugins.json` (object or list form, with the
  migration file as fallback) and each manifest; states `enabled / installed-disabled / enabled-but-missing / invalid / absent / unknown`,
  compares `minAppVersion` with the running Obsidian (given, or inferred from the update package name and labelled as inferred) and
  never calls an unknown version incompatible. `html_sessions.py context` lists the result in every resume brief; `visual_assets`
  shares it.
- **Search**: built-in lexical search over notes and session bridges, plus an opt-in loopback bridge to Omnisearch's documented local
  server whose answers are validated (inside the vault, not hidden, right vault, finite score, bounded size) and fall back with a reason.
- **Navigation**: Breadcrumbs, Bases and Graphify stay as before (presentation only, with corrected Breadcrumbs 4 guidance); native
  Backlinks/Outline/Bookmarks/Page preview work on the unchanged bridge; a generated JSON Canvas of canonical prerequisites draws no mastery.
- **Retention**: practice cards are written to a new note from answered questions that have a solution, with no scheduling data; the
  plugin's schedule is never read, so there is one canonical schedule and one ledger.
- **Semantic discovery**: lexical `related` and a suggestion sidecar (`.research-os/plugin-suggestions.json`) that no canonical parser
  reads, every entry `authority: suggestion`, `status: unreviewed`; a canonical relation name cannot be used as a suggestion kind.
- **Audio**: a Listen control in the page using the browser's own speech synthesis (`narration.js`): on-device voices first, online voices
  labelled and never defaulted, lesson text only (never prompts, hints, solutions, widgets or code), equations read in words only where
  the spoken form is unambiguous and otherwise announced, pause remembers the place.
- **Not integrated, with reasons**: Strange New Worlds (a reading aid with no programmatic interface); Smart Connections internals (no
  documented API, source-available licence); Breadcrumbs' `BCAPI` (would blur explicit and implied edges); paid or unofficial TTS services.

Files: `scripts/obsidian_plugins.py`, `scripts/vault_search.py`, `scripts/plugin_exports.py` (new), `assets/html-runtime/narration.js`
(new, bundled by `build.py`), `runtime.js`, `theme.css`, `scripts/html_sessions.py`, `scripts/visual_assets.py`, `scripts/install.py`,
`references/OBSIDIAN_INTEGRATIONS.md` (new), protocol, skill and adapter documents; tests `test_obsidian_integrations.py` (41),
`narration-unit.js`, `html-narration-browser.cjs` (real Chromium, recording fake speech engine).

Executed against the researcher's real vault configuration (read only): Excalidraw 2.28.1 and Breadcrumbs 4.21.14 enabled and
compatible with Obsidian 1.14.4 (inferred from `obsidian-1.14.4.asar`), Bases, Backlinks, Bookmarks, Outline, Page preview and Canvas
enabled, Omnisearch, Spaced Repetition, Smart Connections and Strange New Worlds absent.

Compatibility: `visual_assets.detect_excalidraw` keeps its return shape but now distrusts a manifest that does not name the plugin (one
test fixture was corrected); the resume brief gains an "Obsidian adapters" section; the page navigation gains the Listen control; no
schema or canonical record changed.

Known limitations: no plugin was run inside Obsidian (Excalidraw rendering, a real Omnisearch server, Spaced Repetition parsing the
cards, Canvas opening the file) and no speech was produced on a real device; plugin facts are from manifests on default branches and
public documentation consulted 2026-10-13 and must be re-checked; Spaced Repetition card separators assume its defaults; equations beyond
the supported subset are announced, not read; the app version inference is a file-name heuristic.
