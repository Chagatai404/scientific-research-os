## Dataflow and security boundaries

Learner target → context receipt + bounded canonical planner → recommendation and
prepared plan → native handout / text quiz / lecture / check → saved raw attempt →
review → existing canonical evidence writer. Content generation, stage completion,
local correctness and reading never establish mastery. Replanning must preserve
old answered-question semantics and frozen lecture paths.

Ink is a separate opt-in adapter: session-scoped one-time pairing → bounded vector
events with sequence/ack/deduplication → session-owned assets → explicit frozen
submission → provider-neutral pending review. Never embed huge strokes in core
state or grant remote vault/Node/shell access. Keep CSP unchanged. Threats include
cross-session writes, replay, expired credentials, traversal/symlinks, oversized
payloads, origin spoofing, plaintext LAN interception and duplicate assessment.
Transport, TLS and real-device acceptance are hard gates before claiming shipment.
Current payload bounds: Python state is 8 MiB; the companion bounds serialized
state at 4 Mi characters, both cap events at 10,000. Portable additions must obey
the stricter boundary and keep raw ink outside the state object.

## Risks and manual gates

- Rich scientific content must preserve source locators and scientific checks;
  structural validation alone does not prove teaching quality or effectiveness.
- Legacy deployed runtimes need explicit backed-up installation after approval;
  repository tests do not demonstrate live Obsidian behavior.
- Native handouts must remain readable without turning the player into nested
  scrollbars; test realistic content lengths and narrow viewports.
- Pending free responses, assisted revisions and independent transfer stay distinct.
- Physical tablet, actual Obsidian, audio, real PDF compilation, LAN/TLS and learner
  evaluation remain PENDING until executed, with exact steps documented per slice.
