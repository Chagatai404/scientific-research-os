## Authoritative fields

| Fact | Authority | Not authority |
|---|---|---|
| Capability identity / dependencies / contexts | Validated learning_id, prerequisites, domain (schema-1 subject), projects, goals, courses | Titles, folders, ID prefixes, backlinks or inferred Breadcrumbs edges |
| Learning evidence | Actual reviewed retrieval rows and linked attempts; assessment uses method/outcome/assistance/date/period | Confidence, note existence/promotion, reading timestamps or tutor explanations |
| State / dates / freshness | History-derived assessment; explicit learning_state, first_learned, last_retrieval, next_review summaries must agree | Conflicting hand-edited summaries or invented expiry dates |
| Retention intent | Explicit human retention_target; omission is unspecified | Centrality, activity frequency or silent reassignment to core |
| Research state / approval | Validated typed status/links, recorded human authorization/acceptance, rationale and review references | Mastery, code completion, valid manifests or graph display |
| Source support | EvidenceAtom locators/envelopes/comparisons and recorded verification with fingerprint-bound receipts | Citation/download, library usefulness or diagram arrows |
| Visual reuse | Valid visual registry record and attestation under verification tiers | Successful rendering, Bases appearance or viewing an image |

The learning parser neither grades answers nor verifies the existence/content of
evidence links. Attestations are recorded acts, not authenticated signatures.
Learning metadata ignores unrelated fields; research/visual schemas reject unknown
fields. New fields must not silently disappear through an old parser. Mermaid,
query JSON, maps, dashboards and library indexes are disposable projections.

## Limitations and adaptations

**Domain → Subject → Concept → Project is not fully represented.** The model has
subject-like domain → capability plus project memberships/prerequisites. A
compatible extension and opt-in migration path are required; do not change the
meaning of schema-1 domain in place.

1. Preserve capability granularity: several narrow capabilities may concern one
   broader concept. Do not merge their histories or confuse application skills
   with general concepts. One concept can serve multiple subjects/projects.
2. A computation pass can currently support scalar demonstration; attempts lack
   scope. Old project success cannot imply new conceptual or transfer mastery.
   Method alone does not establish whether an example was project-specific.
3. Tutor already checks prerequisites and transfer. Extend framing, independent
   examples and scoped evidence rather than replacing the learning loop.
4. Retention needs bounded candidate suggestions, not an autonomous scheduler.
   Respect targets and freshness. Importance needs an explicit rationale; activity
   or centrality cannot assign a target or starve older foundations.
5. v0.6.1 requires a visual per block with a documented exception; v0.7 asks for
   selective useful visuals. Slice 5 must reconcile the canonical policy explicitly:
   choose a useful central-idea visual, document no-benefit decisions, avoid one per
   utterance. Preserve source-first and verification tiers. v0.6.2 installed-adapter
   defaults apply to appropriate schematics; quantitative content remains reproducible.
6. Reuse the Excalidraw serializer. Keep its no-overwrite schematic CLI; managed
   generated maps need narrowly owned replacement. Nonempty rows are currently
   required, so empty maps need an intentional empty-state representation.
7. Manim Community is recommended; no executable integration is shipped. Do not
   claim one exists or add a mandatory renderer dependency.
8. No existing paper database exists to extend. A small bibliographic catalog is
   needed, separate from claim evidence. Keep the scout read-only; the coordinator
   handles screened ingestion. Usefulness/access/verification are distinct states.
9. Use TOML `[paper_library]`, not the prompt's illustrative YAML. Personal paths
   belong only in ignored local config. Missing library config must preserve
   search/citation and metadata-only workflows.
10. Follow existing/configured vault paths rather than imposing the illustrative
    numeric layout. Personal conventions use 01 Projects, 02 Knowledge, 03 Sources
    and 90 Templates. Do not reorganize the vault. Formula callouts must be readable
    without custom CSS; distinctive `[!formula]` styling is not assumed.
11. Research schema 1 rejects unknown fields and has no blocks. Reuse typed research
    entities as application contexts where sufficient, adding only explicit optional
    ontology links with parser/docs tests. A block label is not implicitly a project ID.

## Target architecture

Extend the existing Markdown/JSON parsers, without a parallel knowledge database
or persisted research_graph.json.

```text
Canonical ontology: Domain → Subject → Concept (one ID, multiple subjects)
                                             ↓ explicit concept reference
Capability records: learning_id + prerequisites + actual retrieval attempts
                                             ↓ derived dimensions/freshness
Applications: projects + typed research learning_dependencies
                                             ↓ read-only joins
Tutor / retention suggestions / Mermaid / Excalidraw / dashboards

Bibliographic paper record ← source identifiers in EvidenceAtoms
           ↓ primary PDF + metadata; concept/subject/project indexes are views
```

Proposed Slice 1 storage: small opt-in typed Markdown ontology records for domains,
subjects and concepts, using the same restricted scalar/inline-list syntax.
Subjects reference domains; concepts reference multiple subjects and typed relations.
Capability records keep learning_id and explicitly reference a concept. This allows
multiple assessable capabilities for one concept without duplicating it or requiring
promotion. Ontology owns identity/membership/semantic relations; capability records
alone own retrieval evidence. Permanent explanations can point to those records,
or deliberately opt into structural tracking, without copying histories.

Use a versioned learning extension (proposed schema 2) for attempt scope/dimension.
conceptual / transfer / project_application are scopes; recognition / explanation /
derivation / transfer / application are assessment dimensions. These are different
axes. Derive dimensions from their own evidence; absent evidence is unknown/not
assessed, not weak or mastered. Not every capability requires every dimension.
Keep outcome, assistance, period, date, review and evidence references. Do not store
independent mastery counters or flatten dimensions into an aggregate score.

Concept summaries project explicitly linked capability/dimension evidence; ambiguity
stays visible. Existing capability prerequisites remain authoritative for readiness.
Concept prerequisite/builds_on relations guide planning and need cycle validation,
but cannot manufacture prerequisite evidence. related/contrasts_with cycles may be
valid. applied_in refers to explicit applications, not scientific support.

Freeze exact fields, extended table shape and namespace rules in Slice 1 with
fixtures before behavioral edits. A small ontology parser may live beside knowledge.py
but must feed that graph layer and its callers, without a second mastery interpretation.
Research keeps its type-specific vocabulary and human decision gates. Mastery never
resolves a question or changes approval. supports/contradicts views require explicit
evidence/research links, never inference from concept mastery, paper tags or code.
